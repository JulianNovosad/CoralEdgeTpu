# Project Summary: CoralEdgeTpu Detector

The CoralEdgeTpu Detector is a real-time object detection application designed for embedded systems, likely a Raspberry Pi with a Coral Edge TPU. Its primary purpose is to capture video from a camera, perform accelerated object inference using a TensorFlow Lite model on the Edge TPU, overlay detection results (bounding boxes and labels) onto the video stream, and then distribute both raw and overlaid video, along with detection metadata, via various network protocols (HTTP MJPEG and UDP).

## Main Components and Their Roles:

1.  **`ConfigLoader`**: Reads application-wide configuration parameters from a JSON file (`config.json`), including model paths, camera resolutions, network ports, and performance settings. This centralizes and externalizes configuration.
2.  **`CameraCapture`**: Interfaces directly with `libcamera` to acquire dual video streams from the camera: a high-resolution stream for general video output/overlay, and a lower-resolution stream specifically tailored for the Edge TPU inference input. It manages camera configuration, buffer allocation, and frame delivery to multiple downstream queues.
3.  **`InferenceEngine`**: The core component for object detection. It loads a TensorFlow Lite model (optimized for Edge TPU), initializes multiple worker threads, each with its own interpreter, and applies the Edge TPU delegate for hardware acceleration. It consumes resized image frames from `CameraCapture`, performs inference, and pushes `DetectionResult` objects to an output queue. Includes robust performance monitoring.
4.  **`VideoOverlayProcessor`**: Consumes raw image frames (from `CameraCapture`) and detection results (from `InferenceEngine`). It overlays the bounding boxes and a colored square (as a placeholder for labels) directly onto the pixel data. The modified image is then compressed into MJPEG format using `libjpeg-turbo` and pushed to an MJPEG output queue.
5.  **`MjpegServer`**: A simple HTTP server that streams the overlaid MJPEG video from `VideoOverlayProcessor` to connected clients (e.g., web browsers) using the `multipart/x-mixed-replace` protocol. It supports multiple concurrent clients.
6.  **`UdpSender`**: Transmits JSON-serialized `DetectionResult` data over UDP to a specified target IP and port. This provides a lightweight way to send metadata for external consumption.
7.  **`UdpVideoSender`**: Compresses raw image frames (from `CameraCapture`) into JPEG format and sends them as fragmented UDP packets to a specified target. This offers a low-latency raw video feed option.
8.  **`ProcessSupervisor`**: A generic, robust utility for managing external child processes (like `rpicam-vid`). It handles launching, monitoring, restarting (with exponential backoff and cool-down), and reading output from these processes, including a watchdog for inactivity. This is used by `MjpegCapture` (though `MjpegCapture` was commented out in `main.cpp`).
9.  **`JpegCompressGuard`**: A RAII C++ wrapper around `libjpeg-turbo` for efficient JPEG compression of raw pixel data into memory, incorporating custom error handling and destination management. Used by `VideoOverlayProcessor` and `UdpVideoSender`.
10. **`Logger`**: A thread-safe, asynchronous singleton logging utility that writes messages (INFO, WARNING, ERROR, JSON) to both the console and timestamped JSON log files. This minimizes performance impact and aids debugging.
11. **`pipeline_structs.h`**: A central header defining common data structures (`ImageData`, `DetectionResult`, `ImageFrame`) and a generic `ThreadSafeQueue` template, along with type aliases for all inter-module communication queues. This ensures thread-safe data transfer across the pipeline.

## Inferred Design Goals:

*   **Real-time Performance**: Emphasis on low-latency video processing and inference, utilizing Edge TPU acceleration, multi-threading, asynchronous I/O, and highly optimized components like `libjpeg-turbo`.
*   **Robustness and Reliability**: Extensive error handling, process supervision with restart policies (exponential backoff, cool-down), and graceful shutdown mechanisms to ensure continuous operation in an embedded environment.
*   **Modularity and Flexibility**: The pipeline is broken down into distinct, interchangeable modules communicating via thread-safe queues. Configuration is externalized, and multiple output streams (overlaid HTTP, raw UDP video, UDP bounding boxes) are supported.
*   **Efficiency**: Direct `libcamera` interaction, efficient pixel data manipulation, and optimized data transfer mechanisms (e.g., `mmap`, `memcpy`, custom `libjpeg` destination manager).
*   **Debugging and Monitoring**: Comprehensive asynchronous logging with JSON output and a `--dump-state` command-line option for inspecting module states facilitate development and operational insight.

## Identified Discrepancies and Potential Improvements:

*   **Color Format Mismatch**: `CameraCapture` is configured to request `RGB888` from `libcamera`, but `VideoOverlayProcessor::draw_overlays` explicitly states it assumes `BGR` format for pixel manipulation. This will lead to incorrect color rendering of bounding boxes. This needs to be resolved by either converting to BGR after capture, or adjusting drawing logic to RGB.
*   **JSON Escaping**: The `Logger::log_json` implementation performs basic string concatenation to form JSON. It explicitly notes that it assumes message content is safe or will be escaped upstream. This is a potential vulnerability for malformed JSON if log messages contain unescaped quotes or special characters. A dedicated JSON library should ideally be used for robust JSON output.
*   **`UdpSender` / `UdpVideoSender` Construction Errors**: These modules log errors during construction if socket creation or IP parsing fails but do not throw exceptions. This means `start()` might be called on an invalid object. While `start()` does check for `sockfd_ == -1`, it's a "fail-fast" approach at a later stage, and a more robust design would involve throwing exceptions during construction or handling the failure more explicitly.
*   **Unused OpenCV Include**: `<opencv2/opencv.hpp>` is included in `camera_capture.cpp` and `mjpeg_server.cpp` but not used in the analyzed snippets. This indicates potential dead code or a legacy include that could be removed.
*   **`InferenceEngine` Delegate Ownership**: A comment in `inference.cpp` highlights a complex and potentially fragile delegate ownership/destruction scenario if `tflite::Interpreter::AllocateTensors()` fails after `ModifyGraphWithDelegate()`.
*   **Log Rotation**: The `Logger` notes that runtime log rotation based on time or size is not implemented, only rotation on startup.
*   **`static uint16_t sequence_number` in `UdpVideoSender`**: If multiple `UdpVideoSender` instances are created, they would share the same sequence number, potentially causing issues for a receiver trying to reassemble frames. Given `main.cpp` creates only one, this might be an intentional scope decision, but it's a point of caution.
*   **`ImageResizer` and `FrameDisplayer` Obsolescence**: The `main.cpp` clearly indicates these modules were removed/made obsolete due to new camera capabilities. This is a positive sign of optimization and design evolution but highlights how rapidly embedded system architectures can change.
*   **`MjpegCapture` in `main.cpp`**: The `mjpeg_capture` module is not used in `main.cpp`. The current `main.cpp` code instantiates `MjpegServer` with `overlaid_mjpeg_to_http_queue`, which is populated by `VideoOverlayProcessor`. This suggests that the MJPEG stream for HTTP is derived from the *overlaid* video, not a raw MJPEG stream from `MjpegCapture`. The `ProcessSupervisor` is also not directly used in `main.cpp` to manage an `rpicam-vid` instance. This means the `ProcessSupervisor` template is not currently instantiated or used.
